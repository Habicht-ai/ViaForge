## Reproduction driver

`py -3 tools/test-servers/hotbar_probe.py --version 26.2 --label manual-repro`

The driver starts a retained isolated fixture using the exact installed Paper
126 / protocol 776 / Grim `2.3.74-8eb5f28`. Bindings are loopback only. A new
non-OP account performs Creative clicks with Grim ON and no bypass permissions.
It uses the actual Forge client, native Creative handlers, hotbar key bindings,
right-click logic and connection. It does not inject replacement placement or
inventory packets. The current lab helper is copied with its SHA recorded; it
is newer than the helper on the ordinary 26.2 profile (13,014 vs 11,548 bytes).
Both helpers are observation/check-control helpers; no live helper is replaced.

All world edits and `clear` commands target the new fixture and its new account.
The fixture world is backed up before construction. Existing profiles/worlds
are not opened. Client options and ViaForge configuration are restored after
the run; owned clients/servers exit normally.

Cases cover initial placement and return to the first slot, mouse clicks,
quick-craft dragging, catalog number-key selection, menus kept open over multiple
ticks, first/second/last hotbar slots, a following empty slot, and reconnecting
with saved quartz followed by dirt in the adjacent slot. Quick-craft is driven
through the native handler's begin/add/end operations. Paced mouse tests invoke
press/release separately and close through `EntityPlayerSP.closeScreen`, including
the real close-window packet. Ordinary non-paced GUI tests also use that close
path now. Block placement is checked on the authoritative server at 0,64,0;
selected slot is checked with an entity NBT condition. Client inventory and
selection are separately checked after placement. Each click case lasts 2 s.

Every run retains `sources.json`, `report.json`, server console, client console,
native/wire JSONL, Grim events and world backups below `run/test-servers/hotbar-*`.
The first parser failure and incomplete drag-gesture attempt are retained as
failed test-driver runs, not application failures. Early successful runs closed
the GUI directly; they are supplementary evidence only. Later runs use the full
native close path and add client/server slot assertions.

## Normal development-client recording

The development JAR used by `build.bat runClient` now installs `HotbarTrace` for
ordinary connections to loopback servers, independently of the automated driver.
It records changed hotbar/selection/screen/container state and outgoing creative,
held-slot, close/use packets plus incoming slot/content/held-slot updates. This
starts on the next client launch; existing client processes are not replaced.

Files: `run/ViaForge/diagnostics/hotbar-<time>.jsonl`, one per connection,
at most 4096 events / 4 MiB. Network callbacks queue observations; disk writes
are batched on client ticks. No chat, login tokens or account credentials are
recorded. The observer neither sends nor cancels packets nor changes inventory.
There is no instrumentation in the release JAR. Old diagnostic files are kept.

If the symptom recurs, retain that connection's JSONL and note the approximate
time and occupied/selected slots. This should distinguish a wrong creative slot,
a later server inventory update, a selection disagreement, or a display-only
problem. A replay from that evidence is the next step before changing production
code. The existing test sequence alone has not exposed a faulty translation.
